**Architecture:** Twin of Android `:feature:cycle`. Cycle is **not a tab** (Android M9, S-23): it is pushed from the More placeholder now and from the Home card in M7.

**Tech Stack:** Swift 6 / SwiftUI, GRDB (`SalusDatabase`), `SalusReminder` (M3 engine, notification path only), `SalusSettings`, swift-testing.

**Spec:** `salus-android/docs/ios-v1-plan.md` — §4 (module structure), §6.1 (window), §7 (banned claims), §8 (`CycleScreen`, `CycleDayScreen`), iOS-M6 entry ("Calendar + prediction overlay, symptom logging, `CyclePredictor` (port the 11-case table). ### Task 12b — the tab bar shows only on a tab's root

Not in the plan. Raised by the user on 2026-08-29 while Task 12 was in review: iOS kept the tab bar
on pushed screens, where Android hides it (`SalusApp.kt:133-136` — *"the bottom bar only exists while
a top-level destination is visible; pushed detail/editor screens get the full height"*). Kotlin asks
the flattened stack whether the key on top is a top-level one; iOS holds one `NavigationPath` per
tab, so the same question is *is this tab's path empty?*, which is why the predicate landed on
`TabBackStacks` and not in the shell:

- `SalusNavigation` gained `public func isAtRoot(_ tab: Tab) -> Bool { path(for: tab).isEmpty }`, per
  tab rather than a `selectedIsAtRoot` convenience (each stack answers for itself; a selection
  flavour would have had no call site).
- `App/RootView.swift` applies `.toolbar(backStacks.isAtRoot(tab) ? .visible : .hidden, for: .tabBar)`
  to each tab's `NavigationStack` — **one line, in the shell**. Nothing in any feature package was
  touched, and every feature's pushed destinations inherit it: medication detail and editor,
  appointment detail and editor, the vitals editors, Reminder health, Cycle and the cycle day log.
- The rule is written into `docs/ios-feature-template.md` ("Shell and navigation-container rule") and
  `CLAUDE.md`, with the clause that *a feature that writes `.toolbar(…, for: .tabBar)` itself is a
  finding*.
- The user asked for that clause to be mechanical, so `.swiftlint.yml` gained the custom rule
  `no_tab_bar_toolbar_in_features` (error, `included:` scoped to `Packages/Features/`) and
  `scripts/lint-custom-rules.sh` gained its planted fixtures. The review found the first regex silent
  on `.toolbar(.hidden, for: .navigationBar, .tabBar)` and on `ToolbarPlacement.tabBar`; the fix round
  widened it to `\.toolbar(Visibility)?\([^)\n]*for:[^)\n]*\.tabBar` and added a second fixture, which
  is the second `no_tab_bar_toolbar_in_features` pair in the CI block above.

This is **parity, not a divergence** — it is listed under shared decisions in the parity ledger

**Recorded divergences from Android — the plan's list, with what execution made of each**

- **(a) `saveDayLog` is one write transaction**, where Android's repository issues `upsertDailyEntry`

  calling the public one would open a second write inside the transaction. Pinned by the DAO's
  atomicity case (an FK-violating link leaves no entry row). Android owes the mirror (follow-up
  below).
- **(b) `CycleReminderSettings`'s setters are synchronous and `config` is a non-throwing

**Further divergences, recorded during execution**

- **(l) `upsertPeriod` and `upsertDailyEntry` use GRDB's `save`, not its `upsert`** (Task 2 — not in
  the brief; found making the brief's own unique-index test pass). Both tables carry a UNIQUE index
  that is **not** the primary key, and the three behaviours part company exactly there. GRDB `upsert`
  emits `INSERT … ON CONFLICT DO UPDATE` with no conflict target, so a new id landing on a taken
  `(profile_id, start_date)` **silently overwrites** the row already there. Room's `@Upsert` catches
  any uniqueness failure and retries as `UPDATE … WHERE id = ?`, which with a new id matches no row,
  so it **silently writes nothing** (`EntityUpsertAdapter.kt:44-51`, `checkUniquenessException` at
  `:215-224`, read from the extracted `room-runtime-2.8.4-sources.jar`). GRDB `save` is
  update-by-primary-key or insert: the ordinary edit still updates its own row, and the collision
  surfaces as the `DatabaseError` the index exists to raise. **The brief's stated behaviour is
  neither library's default, and `save` is the construct that produces it.** It is a rule any future
  `…Record` with a non-PK unique index will need. Android owes the decision (follow-up below).
- **(m) `toSymptomLinks` sorts the symptom ids before mapping** (Task 5). Kotlin's `Set<String>` is a
  `LinkedHashSet` and walks insertion order; a Swift `Set`'s iteration order is seeded per process,
  which would hand the same day's links to the DAO in a different sequence on every launch. The table
  is identical either way — the primary key is `(entry_id, symptom_id)` and `replaceEntrySymptoms`
  deletes before it writes — so the sort buys a reproducible *write*, not a different result.
- **(n) `observeSymptoms()` seeds eagerly, at stream creation** (Task 5), not at first iteration. The
  seeding task starts when the stream is built, so a caller that creates the stream and never
  iterates it still writes the eight starter rows. Pinned by the first-collection and
  second-collection cases; recorded because it means the catalog can exist before anything has read
  it.
- **(o) `cycle_back` has no reader** (Task 11). SwiftUI's system back button on the shell's
  `NavigationStack` pops the very path `Navigator.pop()` mutates, and iOS 17 offers no supported way
  to relabel it — hiding it would also kill the interactive swipe-back. Exactly the divergence
  `MedicationEditorScreen` and `AppointmentEditorScreen` already record for `editor_back` /
  `appointments_back`; the key stays in the catalog because the catalog is Android-verbatim.
- **(p) `saveTask.replace(with:)` cancels an in-flight save** (Task 11) where Kotlin's double tap
  launches two coroutines and runs both. Benign — the write is an upsert of the same row either way —
  but it is a real difference and it is noted in the file header. Android's double-tap race is a
  follow-up below.
- **(q) Selecting a lead-days option also emits `reminderDialogDismissed`** (Task 10, benign) — see
  (e). Both paths are idempotent closes on the ViewModel; the same "any dismissal reports itself"
  wiring `MedicationsScreen.swift` already ships.
- **(r) The tab bar is hidden on every pushed destination** (Task 12b) — **parity, not a divergence.**
  Listed here because the plan's letters run to (r) and a reader looking for it should find it, but it
  goes into the parity ledger's shared-decision section, not its divergence table.

Two more, smaller, recorded at their call sites rather than given letters: the mappers are static
functions on an `enum CycleMappers` namespace rather than extensions on the records (an extension
would add `toDomain()` to a *public* `SalusDatabase` type for every file in `FeatureCycle`, which is
what CLAUDE.md's "records never leave `SalusDatabase`" rule protects — and it is the brief's own
shape, recorded only because it differs from the M5 file it is otherwise modelled on); and
`formatMinuteOfDay` passes no locale where Kotlin's `String.format(locale, "%02d:%02d", …)` localises
the digits — both project locales use Latin digits, so nothing renders differently.

### Android follow-ups opened by this milestone

`salus-android/` is code-read-only for the whole of iOS-M6 — the only write is the parity-ledger docs
commit — so these are recorded here and in `docs/parity-ledger.md` as unnumbered `A?` rows for the
user to number into spec §11. **iOS-M3/M4/M5 opened twenty that the ledger numbers `A14`-`A33` as
*proposed*; §11 has never been extended past A13.** Re-check §11 before writing these in.

- **A tapped cycle notification is a dead end on Android** — the extras are written and never read.
  iOS pushes `CycleKey` onto Home (divergence (c), ruling 2 of the plan). Either wire the Android tap
  or delete the extras.
- **`averageCycleLength` is computed and never rendered.** `CyclePredictor` returns it, the ViewModel
  carries it in state, the Kotlin test asserts it, and `CycleScreen.kt` draws nothing with it. Ported
  faithfully, unrendered on both platforms. Render it or drop it from the model.
- **The calendar ViewModel discards its use-case results.** `startPeriod`, `endPeriod` and
  `saveCycleDay` all return a result type with error cases, and the ViewModel ignores every one — a
  rejected start (already open, or a duplicate on the same day) is silent on both platforms. Ported
  faithfully. Decide whether the user should be told.
- **`saveDayLog` is two separate writes on Android**, where iOS runs one transaction (divergence
  (a)). A failure between them leaves a day beside the symptom set of its previous version.
- **`SalusPillButton` is now a shared `SalusUI` component on iOS**, and Android's twin lives in
  `core/ui`. Three inline iOS sites still bypass it (appointment detail, medication detail,
  `SalusEmptyState`) — an iOS chore, listed so the Android side knows the component now exists on
  both.
- **`nav_cycle` is declared and referenced nowhere.** iOS did not port it: it is not in the 56-key
  set, so there is no key-set-parity obligation. Same class as `appointments_upcoming_header` (A20).
- **A double tap on the day screen's save starts two writes** (`CycleDayViewModel.kt`). Kotlin
  launches two coroutines; iOS cancels the first (divergence (p)). Benign because the write is an
  upsert, but it is an unguarded race on Android.
- **Room's `@Upsert` silently drops the write when the conflict is a non-PK unique index**
  (`CycleDao.upsertPeriod`, `upsertDailyEntry`). A new id on a taken `(profile_id, start_date)` retries
  as `UPDATE … WHERE id = ?`, matches no row, and writes nothing — no error, no row. iOS raises the
  `DatabaseError` the index exists to raise (divergence (l)). This is a correctness question on
  Android, not a style one.
- **The iOS-only M6 tables have no Android twin**, in the shape A21/A33 track M4's and M5's:
  `LocalDate`'s 15 arithmetic cases (month clamping, leap February, `isoDayNumber`), `CycleDao`'s 17
