# Salus iOS — project rules

A 1:1 manual Swift port of `salus-android`. Every rule below names its **enforcement point**:
a lint rule, a test, or "review" (a human/agent check with nothing mechanical behind it yet).
A rule with no mechanism is still binding — it just costs more to break unnoticed.

Port contract (source of truth, versioned in the Android repo):
`salus-android/docs/ios-v1-plan.md` (§ references below) ·
`salus-android/docs/design/design-tokens.md` · `salus-android/docs/contracts/backup-format-v1.md`.

- **Language rule (project-wide):** everything written into the repository is **English** — code comments, commit messages, branch names, PR descriptions, and every `.md` file. The only exception is conversation with the user, which stays Turkish. User-facing product strings are a separate matter: they ship in the `.xcstrings` catalogs, Turkish (default and fallback) and English, and Turkish UI copy is quoted verbatim. — *enforcement: review.*
- **Read first:** `docs/superpowers/STATUS.md` (where the work stands), the port contract above, `docs/ios-feature-template.md` (MANDATORY when creating a new feature) — then the rule file of every area the task touches. Toolchain and CI usage: `README.md`. New plans, specs and status files live under `docs/superpowers/`; the iOS-M0…M14 plans in `docs/plans/` are history. Start sessions inside this repository; the Android twin is `../salus-android`, where the port contract and `docs/parity-ledger.md` live.
- **Rules by area** (`.claude/rules/`, loaded by path; subagents read them explicitly):
  | File | Applies to | Scope |
  |---|---|---|
  | `architecture.md` | `**/App/**`, `**/Packages/**`, `**/project.yml` | settled decisions, layer rules, the `Calendar` and `shared` carve-outs, port fidelity, persisted keys, Room schema copies |
  | `design-system.md` | `**/Packages/SalusUI/**`, `**/Packages/SalusDesignSystem/**`, `**/Packages/Features/**`, `**/App/**` | tokens, theme environment, palettes, bars, toolbar shape, shared components, segmented tabs |
  | `copy.md` | `**/*.xcstrings`, `**/*Strings.swift`, `**/Packages/Features/**`, `**/App/**` | banned health claims, disclaimer, TR + EN parity, placeholders, upper-case overlines |
  | `build.md` | `**/project.yml`, `**/Salus.xcodeproj/**`, `**/Package.swift`, `**/scripts/**`, `**/.swiftlint.yml`, `**/.swiftformat` | XcodeGen, local == CI, lint gates, custom-rule gate, test gate, pinned toolchain |
  | `planning.md` | `**/docs/**` | process, specs, plans, status, handover, rulings, design work, manual QA, parity ledger |
- **Settled decisions** (do not relitigate; details in `architecture.md`): the dependency allowlist is closed at three — GRDB, `purchases-ios`, `firebase-ios-sdk`, each only with the milestone that needs it; offline-first, local-only: no backend of ours, no analytics, no ad-hoc networking; Swift 6 language mode with strict concurrency everywhere, never downgraded to silence an error; deployment target iOS 17 and bundle identifier `com.alicansekban.salus`. UI is SwiftUI over GRDB, with Swift Charts only inside `SalusUI`.
- Code comments explain **why**, not what.
- **Checks:** `/salus-gates` (steps `toolchain`, `lint`, `lint-rules`, `test`, `build`; `all` runs the five in `scripts/ci.sh` order, ~15 min — run it in the background). Raw gates for other harnesses: `scripts/ci.sh` (or its five scripts); hooks are tested by `.claude/hooks/test-hooks.sh` (set `SALUS_ANDROID_DIR` to an Android checkout that has the hooks). Run `scripts/ci.sh` before every integration; `Salus.xcodeproj` is generated by `xcodegen generate`, never hand-edited.
- **Handover:** start from `docs/superpowers/STATUS.md`; after every task update the milestone's status file (`/salus-handover`), at the end of a milestone `STATUS.md` too. Rules only here — hashes, counts and dates live in those files and in git.
- **Working setup:** the controller coordinates through `superpowers:subagent-driven-development` and dispatches the Salus agents — `salus-implementer` (implementation and fixes), `salus-reviewer` (task reviews and scoped re-reviews), `salus-architect` (planning drafts). Fix loop ≤ 5; the controller reviews the whole branch itself and checks diffs and test output, never only a report. Manual QA on a simulator or device is the owner's job: agents write `docs/qa/m<N>-manual-qa.md`, never drive a simulator or device.
- **Models:** the Jev router hook (`~/.claude/hooks/jev-router.py`) picks Sonnet 5.5 or Opus 5.5 per dispatch for `salus-implementer` and `salus-reviewer` (`jev-min-model: sonnet`); the controller passes **no** `model` to them. `salus-architect` is pinned to Opus. A model the owner names for a task is passed explicitly for that task only.
- **Checkout policy:** a big milestone's whole scope stays on one `m<N>-*` branch — nothing merges to `main` until every task is done and the owner's QA has run. Independent tasks may run in parallel worktrees (`git worktree add ../wt-<x>`) on side branches, then rebase onto the milestone branch.
- **Linear history:** when green, `git rebase main` the branch, then `git merge --ff-only` into `main`. No merge commits, never `--no-ff`.
- Commit and push only on the owner's word. Once the owner authorizes executing a plan, commit its tasks as the plan says without asking again; preparing documents alone is not that authorization.
- A decision that touches both platforms records a row in `../salus-android/docs/parity-ledger.md`; behaviour may differ from Android only where the port contract (§6) records a decision.
